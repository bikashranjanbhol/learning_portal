A system design interview tests whether you can reason about trade-offs under
incomplete information. Interviewers are listening for how you narrow an
ambiguous problem, pick a design, and stay honest about what it costs. They are
not checking whether your diagram matches a reference architecture. Candidates
who memorise diagrams fail the moment a follow-up question moves off the script.

That distinction drives everything else in this course, so it is worth making
concrete before we design anything.

## What does the interviewer actually score?

Most rubrics, whatever they are called internally, come down to four things.

| Signal            | What a strong answer looks like                                          |
| ----------------- | ------------------------------------------------------------------------ |
| Problem framing   | Asks what "design Twitter" means before drawing boxes                    |
| Trade-off honesty | Names the cost of each choice unprompted                                 |
| Depth on demand   | Can go three levels deeper on any component when asked                   |
| Course correction | Changes the design when given new constraints, without getting defensive |

Notice what is missing: knowing the "right" answer. There isn't one. Two
candidates can propose different architectures for the same prompt and both
score well, provided each can say why they chose theirs and what they gave up.

<Callout variant="gotcha" title="The most common failure is not technical">
  Candidates lose points for confidently asserting a number they cannot justify — "we'll need
  200 servers" — far more often than for choosing the wrong database. An estimate you can derive
  beats a number you remember.
</Callout>

## Why does ambiguity come first?

"Design Twitter" is not a specification. It is an invitation to ask questions.
Before writing anything down, you need to know roughly what scale you are
serving, which operations dominate, and what the system is allowed to get wrong.

Consider how much the answer changes based on one unknown — the read-to-write
ratio:

```ts
// Two systems, same prompt, entirely different designs.
type Workload = {
  readsPerSecond: number;
  writesPerSecond: number;
};

function shape(workload: Workload): string {
  const ratio = workload.readsPerSecond / workload.writesPerSecond;

  if (ratio > 100) {
    // Reads dominate. Cache aggressively, denormalise, precompute timelines.
    return 'read-heavy: fan-out on write';
  }

  if (ratio < 1) {
    // Writes dominate. Fan-out on write would amplify load catastrophically.
    return 'write-heavy: fan-out on read';
  }

  return 'mixed: hybrid, split by follower count';
}
```

The same prompt produces two incompatible architectures depending on a number
nobody gave you. Asking for it is not stalling — it is the first real design
decision, and interviewers notice when you skip it.

### How many questions is too many?

Three to five, in the first few minutes, then move. Candidates who spend fifteen
minutes gathering requirements run out of time to design anything, which reads
as avoidance rather than rigour.

The questions worth asking almost always fall into these buckets:

1. **Scale** — how many users, how much data, what growth
2. **Operations** — which reads and writes dominate
3. **Consistency** — what is allowed to be stale, and for how long
4. **Failure** — what happens when this is down, and who notices

## What does "trade-off" mean concretely?

It means naming the cost of a choice in the same breath as the choice.

> "I'd cache the timeline in Redis. That gets reads under 10ms, but it means a
> follower can see a stale timeline for up to 30 seconds after a post, and I'm
> now carrying a second system that can fail independently."

Compare that to "I'd add Redis for caching." Same decision. The first tells the
interviewer you understand what you just bought and what you paid. The second
tells them nothing.

<Callout variant="tip" title="A phrase worth practising">
  "The cost of that is…" — said out loud, immediately after every design decision. It is a small
  habit that changes how the whole interview reads.
</Callout>

## What comes next?

The rest of this course works bottom-up: the primitives first, then the
compositions. Estimation is next, because almost every subsequent decision
depends on being able to derive a number rather than recall one.

You do not need to have memorised anything to continue. You do need to be
willing to say "I don't know, here's how I'd find out."
